Proposed system / Job Service

Durable work, visible outcomes

A compact operating brief for accepting background jobs, processing them safely and returning durable results without tying the design to a language, framework or queue product.

Evidence boundary: this is a synthetic proposed design. No deployed service, customer workload or runtime metric was inspected.

The service in one page

The API acknowledges durable acceptance. Workers own execution. The job store remains the source clients can inspect.

01
PRIMARY RESPONSIBILITY

Turn an accepted request into an inspectable result

Validate the submission, create a stable job identifier, make work available to a worker and persist the final state before reporting completion.

Stable identityOne durable job ID
Visible stateQueued through terminal
Stored resultReadable after completion
BOUNDARY

Acceptance is not completion

An HTTP 202 response confirms that the request entered the durable workflow. It says nothing about when execution will finish.

PERSISTED LIFECYCLE

Every status answers a different operational question

QUEUEDWas the job accepted?
RUNNINGHas a worker claimed it?
COMPLETEDIs the result stored?
FAILEDDoes recovery need a decision?

Responsibilities and hand-offs

Each component owns a narrow contract. Product choices can change without changing the responsibility map.

02
CLIENT EDGE

API service

Authenticates, validates, assigns the job ID and exposes status. It never presents queued work as finished work.

DELIVERY

Durable queue

Makes accepted work available and supports bounded redelivery when a worker disappears.

EXECUTION

Worker service

Claims one job, records RUNNING and performs the operation under an explicit idempotency policy.

SYSTEM OF RECORD

Job store

Holds the request identity, current status, attempt information and final result or failure summary. Client reads resolve here.

RECOVERY GAP

Commit versus publish

Database commit and queue publication are separate boundaries. Use an outbox or equivalent recovery mechanism.

Safe operating rules

The design becomes implementable when retries, terminal writes and client promises have testable boundaries.

03
COMPLETION RULE

Persist the result first

A worker stores the result before it marks the job COMPLETED. A completed status must never point to a missing result.

RETRY RULE

Repeat only when safe

A retry returns FAILED work to QUEUED only when the operation is idempotent or protected by a stable deduplication key.

Invalid input

Reject before runnable work exists. Return a useful client error without allocating worker capacity.

Worker loss

Expire the claim, record the attempt and redeliver within a bounded policy.

Unknown side effect

Stop automatic retry when the external outcome cannot be reconciled safely.

Decisions still required

These choices are deliberately open. They depend on workload, risk and operating environment.

04
TECHNOLOGY
