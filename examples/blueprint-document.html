Job Service

A proposed design for accepting background jobs and returning their results.

Evidence boundary: this is a synthetic proposed specification. No running service or customer project was inspected. All diagrams describe intended behavior.
5Components
4Job states
3Diagram views

1. Purpose and scope

Allow clients to submit work, receive a durable job identifier and retrieve status later. The design is independent of programming language, web framework and queue provider. Authentication, billing and deployment are outside this example.

2. Components

The API validates submissions and persists a queued record. A durable queue passes work to a worker. The job store holds status and results. Queue publication and database commits are separate boundaries: an implementation needs an outbox or equivalent recovery mechanism.

3. Interaction over time

The client receives acknowledgement after a durable queued record exists. It must not interpret HTTP 202 as completed processing. Work can start later; the client reads status by job identifier.

4. States and failures

A job moves from QUEUED to RUNNING only when claimed. A completed result is stored before the job is marked COMPLETED. Processing failure produces FAILED. Retrying work requires an idempotency policy and is allowed only when repeating the operation is safe.

5. Acceptance criteria

  • Accepted submissions return a stable job identifier.
  • Invalid submissions do not create runnable work.
  • Status distinguishes queued, running, completed and failed.
  • A duplicate submission or retry does not repeat a protected side effect.
  • Clients can retrieve the completed result using the job identifier.
